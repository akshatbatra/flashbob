### 🤖 Assistant

Run this command from the workspace root:

```bash
node flashbob/scripts/sync-to-flashbob.mjs
```

**Options:**

| Flag | Default | Description |
|---|---|---|
| `--url <url>` | `http://localhost:5173` | FlashBob server URL |
| `--root <path>` | `cwd` | Workspace root to mirror |
| `--name <name>` | folder basename | Display name |
| `--id <id>` | auto (hash of hostname + path) | Reuse an existing workspace ID |
| `--ignore <globs>` | — | Extra comma-separated patterns to exclude |

For example, to sync against a remote server and reuse a known workspace ID:

```bash
node flashbob/scripts/sync-to-flashbob.mjs --url http://myserver:5173 --id <workspaceId>
```

The script will print the assigned `workspaceId` on first run — pass it via `--id` on subsequent runs to **patch** rather than recreate the workspace.

### 👤 User

Does it automatically generate a random workspace ID if not presented with one

---

### 🤖 Assistant

Yes. Looking at [`sync-to-flashbob.mjs`](flashbob/scripts/sync-to-flashbob.mjs:49), if `--id` is not provided it derives a **deterministic** ID — not random — from a SHA-1 hash of your machine hostname + workspace root path:

```js
const WORKSPACE_ID = args.id ?? createHash("sha1")
  .update(hostname())
  .update(WORKSPACE_ROOT)
  .digest("hex")
  .slice(0, 36);
```

So re-running the script without `--id` will always produce the **same ID** on the same machine for the same path, meaning it patches the existing workspace rather than creating a new one each time. You only need `--id` if you want to explicitly target a workspace created on a different machine or path.

### 1. Where to add the OpenRouter key

React Router / Vite picks this up automatically in dev. Without the key, Jev gracefully falls back to marking every file as relevant (probability `0.5`, score `1`) so the app still works — it just skips real classification.

---

### 2. Does the API follow the OpenRouter implementation?

Yes, it correctly uses the **OpenRouter Decisions API** (`/api/alpha/decisions`), which is a separate specialised endpoint from the standard chat completions one. The implementation looks correct:

- ✅ Endpoint: `POST https://openrouter.ai/api/alpha/decisions`
- ✅ Auth header: `Authorization: Bearer <key>`
- ✅ `Content-Type: application/json`
- ✅ Payload structure uses `model`, `state`, and `questions` as required by the Decisions API
- ✅ Question types are `"noul"` (probability) and `"score"` (0–2 ordinal) — both valid Decisions API primitives
- ✅ Response is read from `data.answers.is_relevant.noul` and `data.answers.importance.score` which matches the response shape

Nothing needs to be changed on the API side — just add the `.env` file with the key.
